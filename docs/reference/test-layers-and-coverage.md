# Test layers and coverage

## Layers

| Layer       | Where the tests are                                                      | Needs                                                                                                            | Runs in                                       |
| ----------- | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| Unit        | `apps/<app>/src/**/*_tests.ts(x)` and `apps/<app>/src/bdd/*_tests.ts(x)` | nothing                                                                                                          | `test:unit`, `test:quick`, pre-push           |
| Integration | `apps/<app>/src/**/*_integration_tests.ts(x)`                            | `flash-be`: the dev stack (`npx nx db:up flash-be`); `flash-web`: nothing, it serves a fake `flash-be` over HTTP | `test:integration`, `test:coverage`, pre-push |
| End-to-end  | `apps/<app>-e2e/steps/*.steps.ts` and the Playwright specs               | the dev stack and the apps                                                                                       | `test:e2e`                                    |

Only the apps use Gherkin. In an app, a **scenario binding** (`src/bdd/*_tests.ts(x)`) runs a scenario from `specs/apps/flash/`.
Everything else is a **plain test** next to the code (`*_tests.ts(x)`): it guards a branch, a rule of structure or an
internal detail. The libraries (`libs/`) and the repository's scripts (`scripts/`) have no Gherkin at all. The choice is
explained in [scenario or plain test](../explanation/scenario-or-plain-test.md). Plain integration tests sit next to the
code as `*_integration_tests.ts(x)`; they are not scanned by the behaviour check.

## Nx targets

The libraries `typekit` and `flash-commons` (`libs/`) have `build`, `typecheck`, `lint`, `test:unit`, `test:coverage` and
`test:quick`. Their tests are plain Vitest files, `libs/*/src/**/*_tests.ts`. They need no Docker. The apps' targets
build both first.

| Target             | App                                   | What it runs                                                                   |
| ------------------ | ------------------------------------- | ------------------------------------------------------------------------------ |
| `typecheck`        | every app                             | `tsc --noEmit` with the strict flags in each `tsconfig.json`                   |
| `lint`             | every app                             | Biome, and warnings fail the run                                               |
| `test:unit`        | `flash-be`, `flash-web`, `flash-load` | unit tests; `flash-be` and `flash-web` also print a coverage report (no floor) |
| `test:unit:watch`  | `flash-be`, `flash-web`, `flash-load` | unit tests in watch mode, no coverage                                          |
| `test:integration` | `flash-be`, `flash-web`               | integration tests                                                              |
| `test:coverage`    | `flash-be`, `flash-web`               | unit and integration together, with the 99% floor                              |
| `test:quick`       | every app                             | `typecheck`, `lint`, and `test:unit` (only the first two for the e2e apps)     |
| `test:e2e`         | `flash-be-e2e`, `flash-web-e2e`       | Playwright, built from the feature files                                       |

Run a target with `npx nx <target> <app>`, for example `npx nx test:coverage flash-be`.

## Coverage floor

The 99% floor is on the combined run: unit and integration tests together. It covers lines, statements, functions,
and branches. The gate is `npx nx test:coverage <app>`. It starts the dev stack, and the pre-push hook runs it for the
affected apps.

Unit tests alone do not reach 99% for `flash-be`, because the database code is covered by integration tests. So
`test:unit` reports coverage without a floor.

Excluded from the coverage denominator:

| Path                                                       | Reason                                                                   |
| ---------------------------------------------------------- | ------------------------------------------------------------------------ |
| `*_tests.ts(x)`, `*_integration_tests.ts(x)`, `src/bdd/**` | test code is not product code                                            |
| `src/routeTree.gen.ts` (`flash-web`)                       | generated by TanStack Router                                             |
| `src/main.ts` (`flash-be`)                                 | process entry point; the end-to-end suite starts and calls it            |
| `src/migrate.ts` (`flash-be`)                              | process entry point; the migrator it calls is covered by integration     |
| `src/seed-sale.ts` (`flash-be`)                            | reads the command line only; the parser and the insert are tested        |
| `src/create-operator.ts` (`flash-be`)                      | reads the command line only; the parser and the account write are tested |

## Behaviour coverage

Every scenario in `specs/apps/flash/` must be bound at the unit layer. It must also be bound at the integration and end-to-end
layers, unless it carries an exemption tag. `npm run bdd:check` checks this without running any tests. It fails when:

- a scenario has no unit binding, or a binding names no scenario;
- an exemption tag has no comment directly above it, or the comment is malformed;
- the alternative proof names a scenario that is not bound at its layer;
- an end-to-end step matches no step definition, or a step definition matches no step;
- a feature file is not linked from the `README.md` in its folder;
- a scenario title is built at run time, so the check cannot read it.

The check writes `generated-reports/behaviour-status.md`. Run it with `npm run bdd:check`.

The check's own tests are plain Vitest files in `scripts/bdd` (`npm run bdd:check:test`). They cover the same defects at
three levels: in process, as a separate command on a temporary corpus, and as a copy of the checker run the way the
repository ships it. The defects are listed once, in `scripts/bdd/support/problems.mjs`.

## How the API end-to-end tests break a dependency

A scenario that needs a failing dependency starts its own `flash-be` process over its own scratch database, so the
shared stack is never touched. Postgres that does not answer is a connection string with no listener. Redis that does
not answer is a TCP relay between the API and Redis that the scenario cuts. A Postgres that refuses one kind of write is
a trigger in the scratch database that raises an error, and dropping it lets writes through again.

## How the web end-to-end tests control the API

The Playwright config starts one built web server with `FLASH_BE_URL` set to a fixed forwarder address (port 18082). The
forwarder lives in the test process. Each scenario starts its own `flash-be` on a free port over its own scratch
database, and the forwarder sends the web server there. A scenario can also cut the forwarder, so the API cannot be
reached, or make it answer with a canned reply, such as a `500`. Scenarios therefore never share state, and none needs
an exemption for an API that is down or unwell.

## Exemption tags

| Tag                   | Meaning                                           |
| --------------------- | ------------------------------------------------- |
| `@integration-exempt` | the integration layer does not bind this scenario |
| `@e2e-exempt`         | the end-to-end layer does not bind this scenario  |

Each tag needs the comment described in [how-to: add a behaviour](../how-to/add-a-behaviour.md#5-exempt-a-layer-only-with-a-reason).

## Pre-push hook

`git push` runs, in order:

1. `npm run lint` (Biome check of the whole repo: format, lint and imports; warnings fail)
2. `npm run docs:check` (RHINO: links, heading structure, README indexes, Mermaid diagrams)
3. `npm run bdd:check:test` (the behaviour check's own tests)
4. `npm run lint:rules:test` (the lint rules for product code, run on sample code)
5. `npm run bdd:check` (the behaviour check)
6. `npx nx affected -t test:quick --base=origin/main`
7. `npx nx affected -t test:coverage --base=origin/main` (unit and integration, the 99% floor)

It stops at the first check that fails. Steps 1 to 5 look at the whole repository; steps 6 and 7 run only for the
projects the change touches, and step 7 needs Docker. End-to-end tests are not in the hook: run them yourself before you
finish a change.
